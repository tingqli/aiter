# cu_scaling_bw：纯读跑满 HBM 需要多少 CU、多少 XCD

## 结论

- **不需要 304 个 CU 全用上。** 每个 CU 保持约 64 KB 读请求在途时，8 个 XCD 每个开 **10 个 CU（共 80 个）就有 97%**，**12 个（96 个）有 99%**，**14–16 个（112–128 个）达到峰值约 3.98 TB/s**。304 个 CU 全用反而略低（3.88 TB/s）。
- **XCD 不能少。** 单个 XCD 最多只能读约 **0.88 TB/s**，开 16 个 CU 和开 38 个 CU 结果一样，说明限制在 XCD 出口，不在 CU 数。6 个 XCD 约 94%，7 个约 98%。
- **本质是全卡在途字节数（Little 定律）。** 读延迟约 1 us，要跑到约 4 TB/s，全卡需要约 4–5 MB 读请求在途。例如 64 个 CU × 64 KB = 4 MB，得到 3.6 TB/s；128 个 CU × 16 KB = 2 MB，只有 3.0 TB/s。每个 CU 单独最多约 80 GB/s。
- **静态平分工作时，CU 必须在各 SE 之间均匀分布，否则由最慢的 WG 决定总时间。** 例如每 XCD 2 → 3 个 CU 时带宽几乎不涨（1.27 → 1.30）；改成动态领取工作块就没有这个现象。
- **对 gemm1 的含义：** gemm1 每个 CU 平均在途约 10 KB，必须用上全部 CU 才能撑到约 3 TB/s，见 `../gemm1_cumask`。

## 实验

`cu_scaling_bw.py`（HIP kernel，用 `torch.utils.cpp_extension.load_inline` 编译）：

- **每个 CU 只放一个 WG：** 每个 WG 声明 64 KB 静态 LDS，也就是一个 CU 的全部 LDS。
- **控制 XCD 和 CU 数：** WG `pid` 按 `pid % 8` 轮流分到各 XCD，只让 `pid % 8 < NX` 且 `pid // 8 < NCU` 的 WG 干活，其余立即退出。
- **验证落位：** 活跃的 WG 读 `HW_ID` / `XCC_ID` 寄存器，统计实际落在多少个不同的 CU、每个 SE 有几个。
- **分工方式：** 共读 2 GiB（远大于 256 MB 的 MALL），默认用原子计数器动态领取 1 MB 一块（dyn=1）；dyn=0 是静态平分。每个线程同时保持 UNROLL 个 16 B 读在途。
- **测量组：**
  - A：8 个 XCD，每 XCD 1–38 个 CU；A'：同上但静态平分；
  - B：1–7 个 XCD；
  - C：每 CU 线程数（256/512/1024）× UNROLL（4/16）。

```bash
python doc-mimo/experiments/cu_scaling_bw/cu_scaling_bw.py
```

## 结果（`results/cu_scaling_bw.txt`）

A 组（8 个 XCD，1024 线程 × 4 个读在途，动态领取）：

| 每 XCD 的 CU 数 | 1 | 2 | 4 | 6 | 8 | 10 | 12 | 14–16 | 20–32 | 38 |
|---|---|---|---|---|---|---|---|---|---|---|
| TB/s | 0.66 | 1.29 | 2.42 | 3.20 | 3.64 | 3.88 | 3.94 | **3.98** | 3.92–3.96 | 3.88 |

B 组（只用部分 XCD）：1 个 XCD 时 16 或 38 个 CU 都是 0.88 TB/s；2 / 4 / 5 / 6 / 7 个 XCD（每个 38 个 CU）分别为 1.56 / 3.03 / 3.55 / 3.73 / 3.90 TB/s。

C 组（每 CU 在途量）：每 XCD 16 个 CU 时，256 线程 × 4（每 CU 16 KB 在途）只有 2.96 TB/s，1024 × 4（64 KB）有 4.00 TB/s。

这个 kernel 的功耗约 200–300 W，时钟约 2.05–2.1 GHz，没有撞功耗墙。
